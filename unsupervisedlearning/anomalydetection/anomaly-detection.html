Goal: "given a dataset of mostly normal examples, learn what "normal" looks like, then flag anything that deviates too much as an anomaly or outlier".

Real data has features per example: . The standard (simple) approach assumes features are independent and models each one with its own 1D Gaussian:
ال Independence = كل feature "بتتصرف لوحدها"، ومعرفة قيمة feature لا تغيّر توقعنا للـ feature الأخرى.

Why multiply? Probabilities of independent events multiply.
If there's a 1/10 chance an engine is very hot and a 1/20 chance it vibrates hard, the chance of both happening together is much rarer than either alone.
This is exactly why The product encodes "all features must be plausible simultaneously."

Note: the independence assumption is technically often violated (features are may be correlated in practice), but the algorithm tends to work fine anyway this is a "good enough" approximation, not a strict requirement.

Why this catches anomalies

If even one feature is way out in the tail of its own Gaussian, is tiny, and since everything is multiplied together, the whole product collapses regardless of how normal the other features look. This is the mechanism: the algorithm flags an example if any feature (or combination) looks unusual relative to what it saw during training.

4. Practical Python Sketch

import numpy as np

def estimate_gaussian(X):
    # X: shape (m, n) m examples, n features
    mu = np.mean(X, axis=0)          # shape (n,)
    var = np.var(X, axis=0)          # shape (n,) uses 1/m by default
    return mu, var

def p_x(X, mu, var):
    # Gaussian density per feature, then product over features (log-sum for stability)
    log_p = -0.5 * np.log(2 * np.pi * var) - 0.5 * ((X - mu) ** 2) / var
    return np.exp(np.sum(log_p, axis=1))   # sum in log-space = product in normal space

def select_epsilon(p_val, y_val):
    best_eps, best_f1 = 0, 0
    for eps in np.linspace(min(p_val), max(p_val), 1000):
        preds = (p_val < eps)
        tp = np.sum((preds == 1) & (y_val == 1))
        fp = np.sum((preds == 1) & (y_val == 0))
        fn = np.sum((preds == 0) & (y_val == 1))
        if tp + fp == 0 or tp + fn == 0:
            continue
        prec = tp / (tp + fp)
        rec = tp / (tp + fn)
        f1 = 2 * prec * rec / (prec + rec) if (prec + rec) > 0 else 0
        if f1 > best_f1:
            best_f1, best_eps = f1, eps
    return best_eps, best_f1

Key implementation notes:

  • Computing as a product of many small numbers underflows quickly → always work in log-space (sum of log-densities), then exponentiate only if you need the actual probability.
  • select_epsilon uses the cross-validation set (which needs labels) to pick the threshold that maximizes F1 this is the standard way to tune when data is highly skewed (few anomalies, many normal examples).

Developing & Evaluating an Anomaly Detection System

This is the most operationally important part of the unit.

Real-number evaluation

The driving principle: while iterating (changing ε, adding/transforming features), you need a single number that tells you whether each change helped. Without it you're guessing; with it, iteration is fast and objective. This is one of the most transferable MLOps habits: fix your metric before iterating on the model.

The unusual data split

Even though training is unlabeled, for evaluation you assume a small number of labeled anomalies (y = 1) among many labeled normals (y = 0). Anywhere from 2–50 known anomalies is typical.

  • Training set: unlabeled, all treated as normal. p(x) is fit only from these. (A few real anomalies that slipped in usually fine.)
  • CV set: many normals + a few anomalies. Used to tune ε and decide feature changes.
  • Test set: same composition. Final, honest estimate.

Lecture example 10,000 good engines + 20 flawed:

Split Good engines Anomalies
Train 6,000 0
CV 2,000 10
Test 2,000 10

Note the key property: positives never touch training. That's what keeps this an unsupervised algorithm labels are used only for tuning and evaluation.

Tuning ε with code

This mirrors the practice lab exactly sweep candidate thresholds on the CV set and keep the one maximizing F1:

def select_threshold(y_val, p_val):
    best_eps, best_f1 = 0, 0
    for eps in np.linspace(p_val.min(), p_val.max(), 1000):
        pred = (p_val < eps)                    # True = flagged as anomaly
        tp = np.sum(pred & (y_val == 1))
        fp = np.sum(pred & (y_val == 0))
        fn = np.sum(~pred & (y_val == 1))
        if tp + fp == 0 or tp + fn == 0:
            continue
        prec, rec = tp/(tp+fp), tp/(tp+fn)
        f1 = 2*prec*rec/(prec+rec)
        if f1 > best_f1:
            best_eps, best_f1 = eps, f1
    return best_eps, best_f1

Practical extension beyond the lecture: F1 is a sensible default, but in production you often pick the operating point by cost e.g., your security team can only review N accounts per day (recall constrained by review capacity), or false alarms erode trust (a precision floor).

The no-test-set alternative

If you have extremely few anomalies (e.g., 2 total), you often can't afford a separate test set. Common practice: train on the good engines, put all remaining data and all anomalies in the CV set, and tune everything there. The tradeoff: after tuning, you have no fair estimate of future performance your ε and feature decisions may be overfit to the CV set. With that little data it's often the only option, but know the risk going in.

Anomaly Detection vs. Supervised Learning When to Use Which

You have some labels why not just use supervised learning? Two questions decide it:

  1. How many positive examples?
    • 0–20 positives (with many negatives) → anomaly detection.
    • Hundreds+ of both classes → supervised learning is viable.
  2. Will future anomalies resemble past ones? Many different types of anomalies, with brand-new types likely to appear → anomaly detection. Future positives likely similar to training positives → supervised learning.

The deep difference: anomaly detection learns a model of normality and flags anything far from it so it can catch a failure mode never seen before. Supervised learning learns what the positive class looks like so it needs enough examples of each type and implicitly assumes future positives resemble past ones.

Application Choice Why
Financial fraud (new schemes emerging constantly) Anomaly detection Future fraud ≠ past fraud
Email spam Supervised Spam keeps selling the same things; future spam ≈ past spam
Manufacturing: previously unseen defects Anomaly detection Brand-new failure modes possible
Manufacturing: known defects (e.g., scratched phone cases) Supervised Same defect recurs → enough labeled examples
Security (hacked machines) Anomaly detection Hackers invent brand-new attacks
Weather prediction Supervised Few recurring classes (sunny/rain/snow)
Diagnosing a known disease from symptoms Supervised Same symptom signature recurs

Choosing & Engineering Features

Why features matter more than in supervised learning

With labels, a supervised algorithm has signal telling it which features to ignore or rescale. Anomaly detection learns from unlabeled data nothing tells it which features are irrelevant. A bad feature distorts p(x) directly. Feature engineering is therefore a first-class activity here, not an afterthought.

Step 1: Make each feature roughly Gaussian

The model assumes each xⱼ is Gaussian, so check it plot a histogram:

import matplotlib.pyplot as plt
plt.hist(x, bins=50); plt.show()

If the histogram is skewed (bunched to one side with a long tail) instead of a symmetric bell, apply a concave transformation that pulls in the long tail (typically the right tail):

  • log(x) requires x > 0. Since log(0) = −∞, guard against zeros: log(x + 1e-3)
  • log(x + c) more generally larger c → weaker transformation; try several values
  • x^p for p < 1 square root (p=0.5), cube root (p=⅓), etc. In the lecture's live demo, x^0.5 improved things, x^0.4 looked best, and x^0.25 overshot

The exploration loop looks like this:

fig, ax = plt.subplots(1, 3, figsize=(15, 3))
ax[0].hist(x, bins=50);                ax[0].set_title("raw x")
ax[1].hist(np.log(x + 1e-3), bins=50); ax[1].set_title("log(x + 0.001)")
ax[2].hist(x**0.4, bins=50);           ax[2].set_title("x**0.4")
plt.show()

You change a parameter, replot, and eyeball it seconds per iteration. (Automatic normality measures exist in the literature, but the instructor's experience is that trying a few values and picking what looks right works just as well in practice.)

Then replace the feature with its transform and critically, apply the identical transform to your CV and test sets. Forgetting this is a classic silent bug: you'd evaluate on data shaped differently from what the model was fit to.

Step 2: Error analysis the iteration loop

After training, the most common failure mode is: p(x) is large for an anomalous CV example the anomaly looks normal in your current features. The remedy is a loop:

  1. Evaluate on CV; find the anomalies the algorithm missed (they have high p(x)).
  2. Inspect one and ask: "What makes me say this is anomalous, even though its features look normal?"
  3. Engineer a new feature that captures it the anomaly should take an extreme value on the new feature.
  4. Retrain and repeat.

Lecture example: a fraudulent account makes a normal number of transactions (x₁ is unremarkable that's why it wasn't flagged) but types at an insane speed. Add x₂ = typing speed. In the 2D plot, the point now stands out on x₂; its p(x₂) factor is tiny, which collapses the product, and it gets flagged. The fitted density doesn't need to be rethought the new feature does the work.

Step 3: Combine features, especially ratios

Data-center example. You start with x₁ = memory use, x₂ = disk accesses/sec, x₃ = CPU load, x₄ = network traffic. Some anomalies get caught; others don't. Suppose a machine behaves strangely with high CPU load but very low network traffic for a video-streaming data center, servers are normally high-high or low-low, so this combination is weird. But neither feature alone is extreme, so neither per-feature Gaussian flags it.

Create a combined feature:

This ratio becomes huge exactly when that failure mode occurs. Variations like CPU²/traffic are also worth trying.

The deeper point: because the model treats features as independent, it can't represent a correlated "normal region" like the high-high/low-low diagonal on its own. Engineered features (ratios) inject that correlation manually. (A variant called the multivariate Gaussian models feature correlations directly, but this course's version deliberately keeps it simple: per-feature Gaussians plus hand-engineered features.)

The Complete Workflow (putting it all together)

  1. Pick the paradigm: few positives (0–20) + novel anomaly types → anomaly detection. Many positives + recurring patterns → supervised learning.
  2. Collect features you expect to take extreme values when something's wrong counts, loads, speeds, and ratios.
  3. Split: train = normal-only (unlabeled); CV and test = mostly normal + the few labeled anomalies. If anomalies ≈ 2, use CV only and accept the lost test-set guarantee.
  4. Gaussianize: histogram each feature, apply log(x+c) or x^p until roughly bell-shaped the same transform on all splits.
  5. Fit μ, σ² on the training set; compute p(x) (log-space if n is large).
  6. Tune ε on CV with F1 or precision/recall at the operating point your business actually needs.
  7. Error-analyze the missed anomalies → new features, especially ratios → back to step 5.
  8. Report test-set performance if you have a test set.

The one-sentence mental model for the whole unit: anomaly detection learns the shape of "normal," then measures how far each new point falls from it. Everything else Gaussianizing features, tuning ε, engineering ratios, using F1 is about making that shape accurate (features) and using it well (evaluation).
